# Pulse — монитор доступности сайтов

Клиент-серверный продукт: пользователь добавляет адреса сайтов, сервис
регулярно их проверяет, показывает статусы в реальном времени и присылает
письма о падениях и восстановлениях. Тестовое задание MadDevs.

| | |
|---|---|
| Backend | Python 3.12, **FastAPI**, SQLAlchemy 2 (async), Alembic, httpx |
| СУБД | **PostgreSQL 16**, Redis 7 (pub/sub для SSE, leader-lock шедулера) |
| Шедулер | отдельный процесс на asyncio (без Celery — см. обоснование) |
| Frontend | **React 18 + TypeScript**, Vite, TanStack Query, Tailwind, Recharts |
| Realtime | SSE (EventSource), живые обновления в UI и на публичной странице |
| Почта | эмуляция: outbox в PostgreSQL + страница «Mailbox» (реальный SMTP — опционально через env) |
| Инфра | Docker Compose; эмулятор проверяемых сайтов `demo-sites` |

Полные обоснования решений — в [`docs/DECISIONS.md`](docs/DECISIONS.md),
промпты и процесс работы с агентами — в [`docs/PROMPTS.md`](docs/PROMPTS.md),
честное состояние проекта — в [`docs/STATE.md`](docs/STATE.md),
сценарии проверки с реальными выводами — в [`docs/PROOF.md`](docs/PROOF.md).

## Быстрый старт

Предварительные требования: **Docker Desktop (или docker engine + compose
v2)**. Ничего больше не нужно — Node, Python и прочее живут в контейнерах.

```bash
cp .env.example .env        # JWT_SECRET и пр. (дефолты подходят для локально)
docker compose up -d --build
```

Первый запуск собирает образы (~минута). Дальше:

| Что | Где |
|---|---|
| Приложение | http://localhost:8080 |
| Демо-вход | `demo@pulse.dev` / `demo1234` (предзаполнен в форме) |
| API (OpenAPI docs) | http://localhost:8000/docs |
| Публичная страница статуса | http://localhost:8080/status/demo-status |
| Эмулятор сайтов (управление) | страница «Demo» в UI, или http://localhost:8090/docs |
| Postgres | `localhost:5432`, `pulse/pulse`, база `pulse` |

Остановить: `docker compose down` (данные останутся в volume).
Сброснуть с данными: `make clean` (= `docker compose down -v`).

## Что внутри (по требованиям задания)

- **Список проверок**: URL, интервал 30с–1ч, таймаут 1–30с, ожидаемый код
  ответа, опциональная ожидаемая подстрока в теле; добавить /
  приостановить / возобновить / удалить / запустить сейчас — всё есть.
- **Группы** проверок с вычисляемым общим статусом
  (operational / degraded / partial_outage / major_outage).
- **Панель статусов**: состояние, время ответа, последняя проверка,
  длительность текущего падения — обновляется сама (SSE).
- **История**: график времени ответа и % доступности за сутки/неделю/месяц;
  журнал инцидентов (начало, конец, длительность).
- **Окна обслуживания**: на проверку или на группу; проверки идут, статусы
  пишутся, письма подавляются (с записью suppressed в Mailbox).
- **Оповещения**: адреса почты на каждую группу; ровно одно письмо «down»
  на инцидент и одно «up» на закрытие; кратковременный сбой (меньше порога
  последовательных неудач, порог настраивается у каждой проверки, по
  умолчанию 3) падением не считается.
- **Публичная страница** статуса по негадаемой ссылке, без входа; показано
  только то, что владелец явно разрешил (флаг проверки + опубликованная
  группа).

## Как продемонстрировать поведение (5 минут)

1. Откройте http://localhost:8080, войдите демо-аккаунтом.
2. Страница **Demo**: переключите `main` → `error`.
3. На **Dashboard** у «Main site» жмите **Run now** (⚡) трижды (порог 3):
   статус станет Down, в **Mailbox** появится письмо DOWN.
4. Пожмите **Run now** ещё сколько угодно — писем больше нет (до
   восстановления).
5. Верните `main` → `ok`, **Run now**: статус Up, в Mailbox письмо UP.
6. **Maintenance**: создайте окно на группу Production на сейчас; уроните
   `main`; 3× Run now → инцидент есть, письма нет (в Mailbox — suppressed);
   удалите окно (или дождитесь конца) — письмо DOWN уйдёт само в течение ~5с.
7. Откройте публичную страницу http://localhost:8080/status/demo-status во
   второй вкладке — статусы меняются там сами, без обновления.
8. `docker compose restart api scheduler`; подождите минуту — проверки
   продолжились с прежними настройками, а простой виден дырой в истории.

Подробные сценарии с фактическими выводами curl — [`docs/PROOF.md`](docs/PROOF.md).

## Разработка и тесты

```bash
make test           # pytest внутри контейнера против отдельной test-БД
make seed-history   # ~90k синтетических результатов на проверку (perf-проверка)
make logs           # хвост логов всех сервисов
```

Backend локально (нужен uv): `cd backend && uv sync && uv run pytest`.
Frontend локально: `cd frontend && npm install && npm run dev` (проксирует
/api на :8000; стек `docker compose up db redis api demo-sites` без frontend).

## Структура

```
backend/    FastAPI: app/api (роутеры), app/checks (раннер+логика инцидентов),
            app/scheduler (процесс-шедулер), alembic/ (миграции), tests/
frontend/   React/TS: src/pages, src/components, src/api, src/lib (SSE)
demo-sites/ эмулятор сайтов с режимами ok/error/dead/slow/flaky
docs/       CONTRACT (источник правды), DECISIONS, PROMPTS, STATE, PROOF
```

## Известные компромиссы и что не делали

См. [`docs/STATE.md`](docs/STATE.md). Коротко: письмо UP, случившееся
внутри окна обслуживания, не отправляется задним числом; SSE-токен в query
(ограничение EventSource); ретеншн сырых результатов 90 дней без
rollup-таблиц. Следующим заходом: rollup-агрегаты, код-сплиттинг фронта,
e2e-тесты Playwright, rate limit на публичные эндпоинты.
