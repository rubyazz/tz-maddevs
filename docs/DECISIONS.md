## 2026-10-05T22:32Z — Старт, выбор стека

**Решение.** Общий стек проекта «Pulse» — монитор доступности сайтов:

- Backend: **FastAPI** (Python 3.12+) + **SQLAlchemy 2.0 async** (asyncpg) + **Alembic**
- СУБД: **PostgreSQL 16**
- Realtime: **Redis 7** (pub/sub) + **SSE** на клиенте
- Шедулер проверок: **отдельный процесс на asyncio** (общая кодовая база с API)
- HTTP-клиент проверок: **httpx** (async, per-request timeout)
- Frontend: **React 18 + TypeScript + Vite**, TanStack Query v5, React Router, Tailwind CSS, Recharts
- Инфраструктура: **Docker Compose**, multi-stage Dockerfiles
- Почта: **эмуляция** — письма пишутся в таблицу `email_outbox` и видны на странице «Mailbox» в UI. Реальный SMTP — опционально через env (aiosmtplib), в поставке выключен.

**Обоснование.**

1. *FastAPI вместо Django/DRF + Celery (вариант из черновика заказчика).*
   Рабочая нагрузка продукта — тысячи лёгких I/O-задач: 50 проверок с
   интервалалом 30 секунд, медленный сайт не должен задерживать чужие
   проверки, параллельный запуск проверки самой с собой запрещён. Это
   классический async-I/O профиль: один процесс-шедулер на asyncio + httpx
   с per-request timeout закрывает все три требования без брокера задач.
   Celery beat спроектирован под статические расписания; суб-минутные
   интервалы, свои у каждой проверки и меняемые на лету, требуют
   django-celery-beat с DatabaseScheduler — лишняя движущаяся часть и
   сложнее доказывать корректность. Django admin не нужен: интерфейс всё
   равно свой (React). Если бы продукт был CRUD-тяжёлым бизнес-приложением
   с административной частью — выбрали бы Django; здесь выбрали async.
2. *PostgreSQL* — требование задания + `date_bin`/`FILTER (WHERE …)` для
   быстрых агрегаций истории.
3. *SSE вместо WebSocket* — поток событий однонаправленный (статусы с сервера
   к клиенту); у `EventSource` бесплатное автопереподключение, не нужен
   отдельный слой (socket.io), проходит через nginx без спецнастроек, кроме
   отключения буферизации. Две вкладки = два независимых подписчика —
   требование «работает при двух открытых клиентах» выполняется тривиально.
4. *Redis* — только pub/sub для фан-аута событий в SSE (устойчиво к
   нескольким uvicorn-воркерам) + leader-lock шедулера. Состояние домена
   живёт в PostgreSQL, поэтому деградация Redis не рушит проверки —
   деградирует только realtime-обновление (клиент всё равно переподхватывает
   снапшот по reconnect).
5. *Почта как outbox в БД* — задание прямо разрешает эмуляцию; при этом
   «письмо пришло/не пришло/suppressed из-за окна обслуживания» становится
   **доказуемым**: строки видны в UI и в API.

**Отвергнутые альтернативы:** Django+DRF+Celery (см. выше); Go-бэкенд
(допустимо по заданию, но Python-стек заказчика выражен явно, а async-Python
справляется с профилем нагрузки с запасом); WebSocket (см. выше);
TimescaleDB (избыточно: на-лету агрегация по индексу `(check_id, checked_at)`
на месячном объёме ~90K строк на проверку — единицы миллисекунд;
rollup-таблица зафиксирована как следующий шаг).

## 2026-10-05T22:35Z — Ключевые доменные решения

1. **Порог падения** — настраиваемый per-check `failure_threshold`
   (1..10, по умолчанию 3 последовательные неудачи). «Кратковременный сбой
   на одну проверку падением не считается» — статус остаётся `up`, в UI
   виден счётчик `failing N/threshold`.
2. **Инцидент** открывается, когда счётчик последовательных неудач достиг
   порога; `started_at` = момент **первой** неудачи серии (`failing_since`
   на строке проверки), а не момент достижения порога — длительность
   инцидента честная. Закрывается первой успешной проверкой.
3. **Письма**: ровно одно «down» на инцидент и одно «up» на закрытие.
   Повторные неудачи в открытом инциденте писем не генерируют.
4. **Окно обслуживания** (на проверку или на группу, можно и то и то —
   ровно одна цель у окна): проверки идут, статусы пишутся, инциденты
   открываются/закрываются, но письма **suppressed** с записью в outbox
   со статусом `suppressed` и причиной (доказуемо в UI). Если окно
   закончилось, а инцидент ещё открыт и «down»-письмо не уходило — его
   отправляет отдельный проход шедулера `window_end_notification_pass`
   (задержка ≤ тик шедулера, не ждём следующей проверки). Recovery-письмо,
   случившееся внутри окна, подавляется и **не** отправляется задним числом
   (осознанный компромисс: «сайт уже поднялся» после конца окна — не
   инцидент; зафиксировано в README «Известные компромиссы»).
5. **Защита от параллельного запуска самой с собой** — атомарный claim на
   строке: `UPDATE checks SET in_flight_until = now()+timeout+10s WHERE
   id = ? AND (in_flight_until IS NULL OR in_flight_until <= now())`. Кто
   получил строку — тот исполняет. Работает и внутри шедулера, и для
   ручного «запустить сейчас» из API, и между репликами процессов.
   Протухший claim самолечится по времени — устойчиво к падению процесса.
6. **Расписание**: `next_run_at = момент диспетчеризации + интервал`. Если
   проверка выполнялась дольше интервала — слоты пропускаются (не
   навёрстываются пачкой, не параллелятся). После рестарта сервера шедулер
   подхватывает сохранённые `next_run_at`; простои не создают результатов —
   в истории это дыра (bucket без данных), а не падение. Availability
   считается только по фактически выполненным проверкам.
7. **Денормализация последнего результата** на строке проверки
   (`last_ok`, `last_status_code`, `last_response_time_ms`, `last_error`,
   `last_checked_at`) — панель статусов читается одним запросом без
   подзапросов на каждую проверку.
8. **История**: агрегация на лету `date_bin`-бакетами: сутки → 5 мин,
   неделя → 1 час, месяц → 6 часов. Индекс `(check_id, checked_at DESC)`.
   Для проверки производительности на больших объёмах — скрипт
   `scripts/seed_history.py` (синтетика, запускается явно, отдельно).
9. **Статус группы** — вычисляемый: `operational` (все up), `degraded`
   (есть paused/unknown среди живых), `partial_outage` (часть down),
   `major_outage` (все down). Не хранится в БД.
10. **Публичная страница** — у группы опциональный `public_slug`
    (unguessable, выдаётся генератором); на страницу попадают только
    проверки группы с `show_on_public = true`. Отдельный публичный SSE-поток,
    фильтрация событий по slug.
11. **Аутентификация** — email+пароль (argon2), JWT Bearer (HS256,Secret из
    env). SSE-подписка авторизуется query-параметром `?token=` (EventSource
    не умеет заголовки; компромисс задокументирован). Регистрация открыта,
    есть сид-пользователь `demo@pulse.dev / demo1234`.
12. **Время** — всё в UTC (timestamptz); фронтенд конвертирует в локальную
    зону. Окна обслуживания задаются в ISO 8601 с зоной.

## 2026-10-05T22:40Z — Прочее

## 2026-10-05T22:50Z — Токены дизайна проверены валидатором; uv + pytest

- Дизайн-токены (§9 CONTRACT.md) прогнаны через валидатор dataviz-skill
  (`validate_palette.js`, dark, surface #0f172a): контраст всех статусных
  цветов и серии линии ≥3:1 — PASS. Фейлы валидатора по lightness-полосе и
  смежным парам к нам не применимы: у нас нет категориальных серий —
  статусные цвета используются по одному и всегда с иконкой/подписью
  (правило скилла «status colors ship with icon + label»), линия — одиночная
  серия. Это осознанное применение скилла, а не отмахивание.
- Пакеты backend — **uv** (pyproject.toml + uv.lock, коммитим лок; Docker
  через ghcr.io/astral-sh/uv): воспроизводимые сборки, скорость, стандарт
  2025+. Тесты — **pytest** (+ pytest-asyncio, respx); DB-тесты — маркер
  `db`, гоняются против test-базы в compose.
