# Состояние проекта (честно)

Дата: 2026-10-06 (UTC). Всё, что описано ниже, проверено на живом стенде
`docker compose up` на машине разработчика; сценарии и выводы — в
[`PROOF.md`](PROOF.md).

## Работает полностью

- **CRUD проверок и групп**: добавление/редактирование/пауза/резюм/удаление/
  ручной запуск «сейчас»; валидация интервалов 30–3600с и таймаутов 1–30с
  на уровне схемы и БД (CHECK-констрейнты).
- **Шедулер**: тик 1с, атомарный claim (проверка не исполняется параллельно
  сама с собой — доказано 409 на повторном ручном запуске и нагрузочным
  тестом), расписание в БД, переживает рестарт, простои не создают ложных
  инцидентов (проверено рестартом api+scheduler на 70с).
- **Инциденты**: порог N последовательных неудач (per-check, 1–10, дефолт
  3), `started_at` = первая неудача серии, закрытие первым успехом,
  длительность в журнале. Проверено e2e и юнит-тестами.
- **Письма**: ровно одно DOWN и одно UP на инцидент, тишина между;
  эмуляция через outbox + страница Mailbox (sent/suppressed с причиной);
  опциональный реальный SMTP через env (не тестировался на реальном
  сервере — не было SMTP в окружении).
- **Окна обслуживания**: на группу/проверку; в окне письма подавляются и
  видны как suppressed; после конца окна при живом падении отложенное
  письмо уходит проходом шедулера (≤ ~5с) — проверено e2e.
- **Realtime**: SSE; две вкладки получают одинаковые события; публичный
  поток фильтруется (только show_on_public + slug группы).
- **История**: агрегация date_bin (сутки/неделя/месяц), график времени
  ответа + полоса доступности + журнал инцидентов; месяц на ~85K строк на
  проверку — 0.17с (скрипт `scripts/seed_history.py`).
- **Нагрузка**: 50 проверок с интервалом 30с — по 2 результата на каждую
  за 75с, ни одна не потерялась/не задвоилась, висящий сайт (таймаут 30с)
  не задерживает остальных, overview 0.28с, публичная страница 0.017с.
- **Публичная страница**: /status/{slug} без входа, только разрешённое.
- **Тесты**: 41 pytest (юнит-домен + DB-интеграция + API-интеграция с
  моками httpx), `make test` в контейнерах; ruff чист.
- **CI**: GitHub Actions — ruff + pytest (сервис postgres) + docker build
  для backend; tsc/vite build + docker build для frontend.

## Известные компромиссы (осознанные)

1. **UP-письмо внутри окна обслуживания не отправляется задним числом**:
  инцидент закрывается, письмо помечается suppressed. Отправлять «сайт
  поднялся» после конца окна посчитали шумом. DOWN-письмо при этом
  уходит по концу окна, если падение живо (по ТЗ).
2. **SSE-токен в query-string** — EventSource не умеет заголовки.
  Альтернатива — cookie-сессии; не стали тащить ради демо. Публичный
  поток токена не содержит вовсе.
3. **Ретеншн сырых результатов — 90 дней**, истории старше нет; rollup-
  таблиц нет (месячная агрегация и так 0.17с на проверку).
4. **Монопольный шедулер** через Redis-lock: масштабирование «шедулеров
  вширь» (шардирование проверок) не делали — лидер один, как и учли в
  контракте.
5. **Один uvicorn-воркер** в демо-стеке; SSE-фан-аут через Redis pub/sub
  уже готов к нескольким воркерам, но конфигурацию не проверяли.

## Не делали и почему

- **E2E-тесты браузера (Playwright)**: вместо них — живой браузерный
  прогон с фиксацией DOM/ошибок консоли (см. PROOF.md); автоматизацию
  отнесли к следующему заходу.
- **Реальная отправка почты**: нет SMTP в окружении задания; транспорт
  реализован (aiosmtplib) и включается env-переменными, но проверен
  только на эмуляции.
- **Интернационализация UI**: интерфейс на английском (стандарт для
  ops-инструментов), локализация не требовалась.
- **Метрики/трейсинг (Prometheus/OTEL)**: вне объёма тестового задания.

## Следующим заходом

1. Rollup-таблицы истории + retention job с партиционированием
   `check_results` по месяцам.
2. E2E-тесты Playwright (логин → уронить сайт → письмо → восстановление)
   в CI.
3. Код-сплиттинг фронта (бандл 645KB из-за Recharts) и виртуализация
   длинных таблиц результатов.
4. Cookie-based SSE-авторизация + refresh-токены.
5. Rate-limit на публичные эндпоинты и на логин.
6. Шардирование шедулера по группам при росте числа проверок.
